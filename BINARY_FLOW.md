# Хранение и обновление файлов

Основной способ работы с teaching - Git-репозиторий с GitHub LFS. Тексты и код сохраняются в обычной истории Git, а PDF, DOCX и растровые изображения - в хранилище LFS. Releases остаются дополнительными скачиваемыми снимками, существующий сайт - дополнительным представлением опубликованного комплекта.

## Какие файлы где находятся

| Материал | Хранение |
| --- | --- |
| Markdown, JSON, CSV, скрипты, CSS, HTML, редактируемые SVG | Обычный Git |
| PDF оригиналов и планов, DOCX, PNG, JPG, JPEG, WebP, AVIF, GIF, TIFF | Git LFS, правила в .gitattributes |
| ZIP готового комплекта | Вложения Releases, локальная папка dist/ исключена из Git |
| Кэш источников, извлеченный текст, временные сборки, частный исходный образец программы | Локально, исключены из Git |

В обычном Git хранится небольшой указатель с SHA256 и размером LFS-файла. В рабочей папке находится сам PDF или документ. Пути файлов одинаковы, поэтому ссылки из планов и каталога не меняются. В дереве публичного репозитория видны сами пути документов, их можно открыть и скачать по отдельности. Возможность встроенного предпросмотра зависит от типа файла и интерфейса GitHub; локально работают обычные просмотрщики.

Неизмененный файл не копируется при каждом коммите. Но новая версия бинарного файла хранится целиком и увеличивает объем LFS. Файлы с одинаковым SHA256 используют один объект даже при разных путях в этом репозитории. LFS отделяет бинарные версии от обычной истории Git, но не отменяет их хранение и учет квот.

В первом импорте 422 официальных PDF и четыре готовых плана: 426 путей, 411 уникальных объектов, 163211530 байт, около 155.7 MiB. Нынешний PDF большого размера занимает около 3.5 MiB. Локальный кэш .git/lfs/objects также занимает место на диске; LFS не делает всю папку .git пустой.

## Клонирование и получение файлов

Git LFS должен быть установлен и инициализирован до клонирования:

```sh
git lfs install
git clone https://github.com/partanskiy/teaching.git
cd teaching
```

Обычный git clone скачивает тексты и оригиналы текущей версии автоматически. Это загрузка примерно 156 MiB LFS-данных плюс обычная история Git. Старые версии всех бинарных файлов при таком клонировании целиком не скачиваются; они загружаются по необходимости при переключении версий. Команда git lfs fetch --all нужна для полной резервной копии или миграции, а не для обычной работы.

Если Git LFS установлен после клонирования:

```sh
git lfs install
git lfs pull
```

Для работы только с текстами можно сознательно пропустить загрузку больших файлов:

```sh
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/partanskiy/teaching.git
```

В такой копии вместо PDF будут указатели, пока не выполнено git lfs pull. Команда python scripts/restore_materials.py в папке курса проверяет SHA256 уже скачанных оригиналов и подготавливает текстовый индекс без сети. Явный --release восстанавливает опубликованный снимок из data/release.json, например если LFS недоступен. Этот снимок может отставать от main; заменять измененные файлы без --replace скрипт не будет.

Кнопку GitHub "Download ZIP" не следует считать эквивалентом клонирования с Git LFS: включение оригиналов зависит от отдельной настройки репозитория. Для получения комплекта без Git используйте явно собранный ZIP из Releases.

## Обновление материалов

1. Начать ветку и изменить исходные данные, код или официальные источники. Оба плана строятся из общих тем, целей, порядка и часов.
2. Пересобрать оба документа при содержательных изменениях. Проверить планы, происхождение оригиналов, сигнатуры и SHA256.
3. Добавить PDF/DOCX обычной командой git add. Фильтр из .gitattributes сохранит указатели, а оригиналы попадут в локальный кэш LFS.
4. Сделать небольшие английские Conventional Commits. Проверить git lfs status и git lfs fsck.
5. Выполнить git push. Hook .githooks/pre-push сначала загрузит необходимые LFS-объекты, затем Git отправит коммиты. Не пропускать hook.
6. Провести PR через проверки и rebase merge. Не переписывать main и не использовать постоянный amend единственного коммита.

После подключения локальных hooks командой git config core.hooksPath .githooks используются и проверка сообщений, и стандартные LFS-hooks. В новом клоне git lfs install также настраивает hooks Git LFS.

CI скачивает только четыре плана, около 0.36 MiB на запуск, и проверяет их согласованность с исходниками. Пересобранный DOCX для сравнения создается во временной папке; изменения только времени создания не добавляют новую версию в LFS. Проверка сообщений коммитов не скачивает LFS. Полный банк проверяется локально перед публикацией новых оригиналов. Не пересобирайте и не коммитьте готовые документы только ради изменения временных меток.

## Квоты GitHub

По [документации GitHub LFS](https://docs.github.com/en/billing/concepts/product-billing/git-lfs), проверенной 01.10.2026, в GitHub Free и Pro включены 10 GiB хранилища и 10 GiB скачиваний за месяц. Квоты общие для аккаунта, а не отдельные для teaching. [Максимальный размер одного файла](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage) для Free и Pro - 2 GB.

Загрузка новых объектов расходует хранилище, но не квоту скачиваний. Скачивания посетителями, клонирования, получение прежних версий и скачивания в Actions расходуют трафик владельца. Если остальные репозитории не расходуют эту квоту, 10 GiB хватает примерно на 65 полных скачиваний нынешнего банка за месяц. Рост коллекции и новые бинарные версии уменьшат этот запас.

При превышении бесплатной квоты поведение зависит от платежного метода и бюджета. Бюджет Git LFS $0 блокирует перерасход, удаленный бюджет допускает платное использование без установленного предела. В этой миграции настройки оплаты и бюджеты аккаунта не менялись. Для жесткого ограничения расходов проверьте бюджет LFS в [настройках аккаунта](https://github.com/settings/billing/budgets); опубликование репозитория само по себе не гарантирует нулевых расходов при превышении квоты.

Удаление файла из текущей ветки или git lfs prune очищает не все серверные версии. Локальный prune управляет локальным кэшем. [Освобождение серверной квоты GitHub](https://docs.github.com/en/repositories/working-with-files/managing-large-files/removing-files-from-git-large-file-storage) требует отдельной процедуры; при будущем переносе нельзя обещать автоматическое освобождение старого хранилища.

## Releases и дополнительный сайт

Готовые ZIP, Word/PDF и SHA256SUMS публикуются по отдельному тегу курса. data/release.json фиксирует конкретный снимок и контрольные суммы. Релиз не нужен на каждый коммит, готовые вложения прежней версии не заменяются молча.

Существующая сборка Pages получает опубликованные файлы из Releases, а не LFS, поэтому не скачивает весь банк за счет квоты LFS. Сайт не является обязательной частью работы с teaching. Если main и опубликованные документы разойдутся, проверка остановит сборку сайта до нового согласованного релиза.

## Будущий перенос в Yandex Cloud

Yandex Object Storage реализует [S3-совместимый API](https://yandex.cloud/en/docs/storage/). Это хранилище объектов. Для стандартного Git LFS дополнительно нужен сервис [Batch API](https://github.com/git-lfs/git-lfs/blob/main/docs/api/batch.md), который принимает SHA256 и размеры, проверяет доступ и выдает клиенту ссылки на скачивание или загрузку. Сами файлы могут передаваться напрямую между Git LFS и Object Storage по подписанным HTTPS-ссылкам.

Адрес LFS-сервиса может быть https://data.partanskiy.ru или https://data.partanskiy.ru/lfs. Префикс /lfs не требуется протоколом: клиент добавляет /objects/batch к настроенному адресу сервера. Для адреса в корне запрос будет POST https://data.partanskiy.ru/objects/batch, для адреса с префиксом - POST https://data.partanskiy.ru/lfs/objects/batch. Выбранный сервис и обратный прокси должны поддерживать один согласованный адрес. Префикс может быть удобен при размещении нескольких API на одном домене; некоторые реализации сами задают поддерживаемые пути.

Сервис может работать на существующем ikaros за NLB; TLS и маршрутизация имени хоста настраиваются на сервере. S3 API бакета можно использовать по стандартному адресу Object Storage. Дополнительный S3-прокси на собственном домене для работы git clone не требуется. Окончательный адрес выбирается при развертывании и проверке сервиса. До миграции математические материалы используют GitHub LFS.

Порядок миграции: развернуть и проверить сервис, скопировать все используемые LFS-объекты, включая прежние версии, сверить SHA256, проверить анонимное клонирование, затем добавить в корень .lfsconfig:

```ini
[lfs]
    url = https://data.partanskiy.ru
```

Историю Git и указатели переписывать не нужно: SHA256 остаются прежними. Публичное чтение должно работать без облачных ключей на компьютерах учеников; запись - только после авторизации. Ключи бакета не публикуются и не входят в .lfsconfig. Точное размещение сервиса и настройка доступа будут выбраны при переносе. В текущем состоянии используется только GitHub LFS; ресурсы и конфигурация YC не изменялись.
