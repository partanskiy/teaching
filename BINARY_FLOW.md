# Хранение, просмотр и обновление файлов

Teaching использует обычную историю Git, вложения GitHub Releases и сайт GitHub Pages. У этих частей разные задачи: Git хранит редактируемые исходники, Releases - готовые версии крупных материалов, Pages - текущий каталог и файлы для просмотра в браузере.

## Что увидит посетитель

| Где открыть | Что доступно |
| --- | --- |
| Страница репозитория на GitHub | README, текстовые планы, реестры, исследования, исходники и небольшие иллюстрации. Крупные PDF не находятся в дереве файлов. |
| Сайт https://partanskiy.github.io/teaching/ | Каталог с фильтрами, ссылки из занятий на задачи, каждый сохраненный документ отдельно. PDF открываются обычным просмотрщиком браузера. DOCX скачивается для работы в текстовом редакторе. |
| Страница Releases | Готовые Word/PDF, ZIP оригиналов, полный комплект для работы без интернета и контрольные суммы. Вложения предназначены для скачивания. |
| Скачанный полный ZIP | Все оригиналы, оба плана и каталог. После распаковки index.html работает без Git, сервера и интернета. |

В первоначальном варианте одного ZIP было бы недостаточно для просмотра отдельного PDF через GitHub. Поэтому сайт получает содержимое архива при сборке и публикует документы по отдельным адресам. Посетителю не нужно сначала скачивать весь банк: браузер получает каталог, а затем выбранный файл. Просмотр PDF всё равно передаёт его данные по сети, но не требует вручную сохранять и распаковывать ZIP.

Небольшие картинки из Git отображаются в Markdown на GitHub и на сайте. Большое фото, сохраненное только во вложении релиза, видно как скачиваемое вложение, а не как автоматически встроенная картинка в README. Для просмотра такого материала на сайте нужно включить его в сборку сайта; для галереи достаточно подготовленных уменьшенных копий. Превью и полноразмерный оригинал могут храниться отдельно.

## Что хранить в Git

| Материал | Способ хранения |
| --- | --- |
| Markdown, JSON, CSV, скрипты, исходники программы | Обычный Git |
| Редактируемые SVG и небольшие оптимизированные изображения к задачам | Git, если размер и частота изменений разумны |
| Сканированные олимпиады, большие фотографии, большие готовые PDF | Releases; нужные для просмотра файлы добавляются в сборку Pages |
| Сгенерированные DOCX/PDF планов и ZIP комплекта | Releases, вне Git |
| Кэши загрузки, извлеченный текст, временные файлы сборки | Локально; в Git не добавляются |

Правило зависит от размера и назначения, а не только от расширения. Бинарный файл в Git допустим. Но новая версия сжатого PDF, DOCX или фотографии может занимать почти столько же места, сколько предыдущая. Даже небольшая видимая правка не гарантирует малого изменения бинарных данных.

Неизмененный файл не копируется при каждом коммите. Основная проблема - накопление измененных версий и размер всей истории, которая передаётся при обычном клонировании. Удаление файла из текущей папки также не удаляет его прежние версии из истории.

## Почему не один постоянно изменяемый коммит

git commit --amend создаёт новый коммит. Старый объект некоторое время остается доступным через reflog и удаляется только при очистке, когда больше нигде не используется. Обновление уже опубликованного коммита требует force push, нарушает ссылки на версии и усложняет работу с другими копиями.

В teaching main защищен, изменения проходят через pull request и объединяются через rebase. История состоит из небольших английских Conventional Commits. Прежние версии документов доступны через релизы, а историю исходников не приходится переписывать ради крупных файлов.

## Как обновляется курс

1. Исправить исходные данные и методические тексты в папке курса. Оба плана строятся из общих тем, целей, порядка и часов.
2. Пересобрать документы, проверить согласованность планов, происхождение оригиналов и контрольные суммы.
3. Сохранить текстовые изменения небольшими коммитами и провести pull request через проверки.
4. Если нужна новая готовая версия, собрать вложения и опубликовать новый релиз. Релиз не требуется на каждый текстовый коммит.
5. Публикация релиза запускает сборку Pages. Сборка скачивает архив и документы по адресам из data/release.json, проверяет SHA256 и публикует каталог вместе с PDF.

Сайт строится из текущего main и зафиксированных в нём версий курсов. Если исходники уже изменены, а соответствующие готовые планы еще не опубликованы, проверка согласованности останавливает публикацию. Несогласованные планы не заменяют действующий сайт.

data/release.json фиксирует версию и SHA256 каждого вложения. SHA256SUMS.txt позволяет проверять скачанные файлы. Готовые версии не заменяются молча: при содержательном изменении используется новый тег. Ссылки на планы привязаны к релизу своего курса и не используют глобальный latest, который со временем может указывать на другой курс.

Обычный git clone не скачивает оригинальные PDF. Для курса после клонирования:

```sh
cd courses/olympiad-math-10
python scripts/restore_materials.py
```

Сайт можно проверить локально из корня репозитория:

```sh
python tools/build_site.py --local-assets
```

У сборки фиксированный каталог _site/, который исключен из Git. Скрипт проверяет контрольные суммы, согласованность планов и ссылки готовых HTML-страниц. При размере сайта 900 MB или больше сборка останавливается с запасом до лимита Pages.

## Место и стоимость

По документации GitHub, проверенной 01.10.2026:

- [Pages доступен бесплатно для публичных репозиториев](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits). Размер опубликованного сайта ограничен 1 GB; мягкий лимит трафика - 100 GB в месяц. Сборка сайта должна завершиться за 10 минут.
- [Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) допускает до 1000 вложений в одном релизе, каждое меньше 2 GiB. В документации не установлен общий лимит размера релиза или трафика его скачиваний. Это не отменяет общих правил использования платформы.
- Стандартные [GitHub-hosted runners для публичных репозиториев бесплатны](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Для teaching используются обычные runners; платные larger runners не настроены.

Промежуточные архивы сборки Actions имеют отдельную общую квоту аккаунта: на GitHub Free включено 500 MB, вместе с другими Actions-артефактами и Packages. Их не следует путать с постоянными вложениями Releases или опубликованным сайтом. Архив развертывания teaching удаляется сразу после успешной публикации; при ошибке он истекает через один день. Платные квоты и бюджеты аккаунта не изменяются.

Нынешние оригиналы занимают около 160 MiB. Сайт с ними значительно меньше лимита. Он содержит только текущие версии материалов, а старые готовые комплекты остаются в Releases. Каждая новая полная сборка ZIP всё равно занимает место во вложениях релизов; вынос из Git не означает отсутствие копий вообще.

Когда коллекция приблизится к лимиту сайта, не нужно переносить все большие файлы в Git. Можно оставить в Pages каталог, превью и выбранные документы, а редко используемые оригиналы давать отдельными ссылками на скачивание. Для очень большой коллекции или значительного трафика следующим шагом может стать отдельное файловое хранилище; его стоимость оценивается отдельно. В нынешней схеме таких платных сервисов нет.

## Альтернатива: Git LFS

[Git LFS](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-git-large-file-storage) хранит в Git небольшие указатели, а бинарные данные - отдельно. Он удобен, когда большие файлы должны выглядеть частью рабочего дерева и скачиваться при клонировании.

Но [квоты LFS учитывают версии файлов и скачивания](https://docs.github.com/en/billing/concepts/product-billing/git-lfs). Новая версия бинарника добавляет полный размер объекта, а не только видимую правку. LFS также не поддерживается непосредственно GitHub Pages. Для текущего банка исходников, публикуемых документов и скачиваемых комплектов Releases и сборка Pages позволяют обойтись без LFS.

Описание объектов Git и поведения amend: [официальная документация Git](https://git-scm.com/docs/gitdatamodel.html).
